# CLAUDE.md: project guide for Claude Code

Read this first. It is the source of truth for how to work in this repository.

## What this is
A free, unofficial, fan-made build planner for the new skill system of The Witcher 3: skills, ability slots, mutagens and mutations.
A static website: no backend, no accounts, no cookies, no analytics. A build lives entirely in the URL hash.
Live at https://w3planner.pages.dev (Cloudflare Pages). Repo: viv4-web/w3planner (public, MIT).
Not affiliated with or endorsed by CD PROJEKT RED. Game names, text, data and art belong to CD PROJEKT S.A.
Never add ads, tracking, accounts, payments or anything that earns money.

- **Vivek** decides product and design.

- **You** (Claude Code, on the Hetzner server as user `w3dev`) implement, test, open pull requests, and deploy when asked.

## Code map (`src/app.js`)
State `S = {lv:[4][20], slots:[16], muts:[4], mres:[12], mact, gear:[9], rs, cons:[8], scr}` (skill levels per tree, equipped skills as `[tree,index]`, mutagen sockets, researched mutations, active mutation; v27: gear numbers and the ruleset; v28: consumable numbers (Potion 1-4, Bomb 1-2, steel oil, silver oil) and the open screen: `'char'`, `'inv'` or, since v29, `'glo'`).
Sections, in order: tooltip engine (`tipText`, compiled `TIPFN` from the game's own scripts), encoding (`enc`, `dec`), rules (`enforceLocks`, `available`, `add`, `rem`, `save`), rendering (`renderTabs`, `tile`, `renderTree`, `renderMutagens`, `renderSlots`, `renderInfo`, `render`), mutations overlay (`openMut`, `renderMut`, `mAct`, `mTip`), hover tooltips, drag and drop (pointer events for mouse and touch), notices (`notify`, `slotNote`, `tryAdd`).
`CFG` comes from `config.js`: the website says `mode "online"`; the offline download says `mode "offline", share false` (it can open links but not create them).
Globals you will use: `TREES`, `MUT` (mutations), `MUTS` (36 mutagens: 9 regular plus 27 special), `SLOT_UNLOCK`, `MUT_UNLOCK`, `MSLOT_UNLOCK`.

## Rules that must never break
1. **No game art in this repo**, ever, not even in one commit (history is forever). The pre-commit hook and `tools/check_no_game_art.py` enforce it. **The same goes for the Glossary's game text and pictures** (v29): they are built into `~/work/w3planner-art/glossary/` and copied into the live build only; the repo holds the code, the tool, `docs/GLOSSARY.md` and the invented fake in `tests/fixtures/glossary`. The public and offline builds show "Glossary content is not included in this build."
2. **Old links keep opening.** Every link ever made must open as the build it was made for (see "Link compatibility" below). Extend the link format only by appending; never renumber or reinterpret existing fields. A failing link test blocks the release.
3. **Link data is untrusted.** `dec()` is strict: it rejects malformed links and clamps every value. Never put link data into `innerHTML`, `eval` or anything executable.
4. **No external requests, no `unsafe-eval`.** The site loads nothing from other hosts. Tooltip formulas are compiled ahead of time.
5. **No silent failures.** When a click cannot do something, tell the user why with `notify()`.
6. **Keyboard and touch work** for every interaction, and the page never scrolls sideways on a phone.
7. **Tests pass before any pull request.** Do not edit `tests/fixtures/tooltips_ref.json` unless the game data itself changed on purpose.
8. Bump `APP_VERSION` (top of `src/app.js`) for releases, and update `static/help.html` when behaviour changes.
9. Never weaken security headers in `static/_headers` or the `protect-main` ruleset.
10. **IDs are never reused or renumbered, only appended.** Skill, mutation and mutagen numbers, tree order and slot positions are part of the link format: a link stores them as numbers. Removing or reordering one silently changes every old link.
11. **No production deploy without the gate** (see "Release gate" below), and none without Vivek's review of the preview. `--promote` only after Vivek has looked at the preview and says yes in this session, in a message written after the preview report. A yes given in advance, inside a brief, or before the preview exists does not count. If a brief says otherwise, stop and ask. Every preview report must end with: the preview URL, what changed visually, and "Waiting for your review of the preview before promoting."

## Link format (`v1`)
`v1.<skills>.<slots>.<mutagens>.<level>.<bonus>.<researched>.<active>`
- skills: 80 skills, 3 per character, 2 bits each (27 characters)
- slots: 16 slots, 2 characters each, value = tree*20 + index + 1 (0 = empty); older links have 12 slots (24 characters)
- mutagens: 4 sockets, `-` for empty or the mutagen index in base 36 (36 mutagens fill one character exactly: a bigger catalogue needs a new format segment)
- level 1-100, bonus points 0-100, researched mutations as a base-36 bitmask, active mutation plus one
- alphabet `A-Za-z0-9-_`; total length at most 400

## Link compatibility
- Fixtures: `tests/fixtures/legacy_links.json` (links made by v7 to v23) and `tests/fixtures/links/<version>.txt` + `.json` (links made by that version's code, with the build each must open as). `tests/linkcheck.py` opens every one of them in the current build, online and in the offline package, and `tests/run_all.py` fails if any opens differently.
- Fixtures are append-only. Never edit or delete an old one; the suite compares them with `main` and fails if one changed. A fixture that "needs" changing means the code broke old links: fix the code.
- Any change to the link format needs all of: a new version marker in the link, a migration so old links still decode, and tests with new fixtures. Make the new fixtures with `python tools/make_link_fixtures.py --version vNN` (it refuses to overwrite).
- Changing the number or order of skills, mutations, mutagens or slots counts as a format change (rule 10).

## Release gate
`tools/deploy.py` is the only way to deploy. Production never gets anything the gate has not passed.
1. `python tools/deploy.py --art-dir ~/work/w3planner-art` (with `cf.env` loaded): game-art guard, the full test suite on the game build (never `--quick`), build, then a **preview** deployment (branch `preview`, never production) and `tests/smoke.py` against the preview URL: page loads, no console errors, every link fixture opens, a new link can be created and reopened. It prints a short report and stops.
2. Vivek can look at the build first with `--serve` (binds 127.0.0.1 only; he forwards the port).
3. Only after Vivek has reviewed the preview and says yes in a message written after the preview report (rule 11): `python tools/deploy.py --art-dir ~/work/w3planner-art --promote --yes`. It refuses unless `dist/game` is exactly the build, from the same clean commit, that passed on preview. After the production upload it **first polls https://w3planner.pages.dev/ itself** (cache-busting query string and no-cache headers, one look every 5 s, up to 5 minutes, `wait_live` in `tools/deploy.py`) until the page's `APP_VERSION` is the version being promoted. If it never is, that is **edge lag, not a test failure**: no smoke test runs, the script says "NOT CONFIRMED, EDGE LAG", and rolls back. Only when the live version matches does it run the smoke tests against the live site; `tests/smoke.py` waits for the plain URL to serve the new `index.html` and version twice in a row to the very browser that runs the checks, and it stops at the first wrong-version page (so a flapping edge counts as the one lag-style failure, not as a dozen test failures). Cloudflare's edge can answer different clients differently for minutes after an upload or a rollback: the v25 and v26 promotes were rolled back by mistake because a Python client saw the new page while the browser, seconds later, still saw the old one, and the first v27 promote (2026-10-01, deployment `6a50b931`) because the browser wait passed twice in a row and the next page load got v26; that run lasted 90 s, not 5 minutes, because the old wait ended as soon as two looks matched and the "new link" check, which is not an edge-lag check, then rolled back at once. If only edge-lag style checks fail it looks again twice, 60 seconds apart; any other failure (script errors, a link that does not open, ...) rolls back at once. That rollback is the only thing it does without asking.
4. If the automatic rollback itself fails, roll back by hand: `POST /accounts/$CLOUDFLARE_ACCOUNT_ID/pages/projects/w3planner/deployments/<previous id>/rollback` (the script prints the id), or use the dashboard (Deployments, "Rollback to this deployment"), and tell Vivek.
The gate logic is tested with a fake Cloudflare in `tests/test_deploy_gate.py` (part of `run_all.py`); nothing in the test suite uploads anything.

## Equipment data (phase 1b: data only, no UI yet)
`data/items.json` is made from the game's own files by `python tools/extract_items.py --game-dir ~/incoming/gamedata --art-dir ~/work/w3planner-art` (re-runnable for a new patch; `--check` verifies the committed file and prints the report). Inputs in `~/incoming/gamedata/`: `bundles/xml.bundle`, `ep1.bundle`, `bob.bundle` (the definition XML, read with `tools/extract/bundle.py`), `inventory/` (icons), `en.w3strings` (`tools/extract/w3dec.py`, v164 UTF-8) and `scripts/` (.ws). Item ids are the game's item names; display names come from `localisation_key_name`; stat labels from `attribute_name_<stat>`. Everything the extractor cites (`file:line`) is looked up in the scripts at run time and the run fails if it is not there. The data is split: `data/items.json` (41 KB: slots, sets with bonuses, rules, `default_ruleset: "ng"`) and one list per ruleset, `data/items_ng.json` (about 640 KB) and `data/items_ng_plus.json` (about 970 KB), each loaded only when that ruleset is chosen. **Never embed them in `index.html`**: write `/*@file:items_ng*/` in `src/app.js` and `tools/build.py` emits `data/items_ng.<hash>.js` (it sets `W3DATA.items_ng`, icon tokens resolved for the variant) and puts only its URL in the page; load it with a `<script>` tag (the CSP has `connect-src 'none'`, so `fetch` is not allowed, and a script tag also works from the offline copy). Cloudflare compresses it on the wire.
- **Bundles** (`tools/extract/bundle.py`: `list`, `extract --glob`, `info`; tests in `tests/test_bundle.py`): zlib, snappy and lz4 are implemented; Doboz is not and is not needed (confirmed by Vivek). The bundles hold definition XML, models and texture headers only: the item ICONS are not in them (the `.xbm` there are CR2W headers; the pixels live in `texture.cache`). The 118 icons `inventory/` lacked (all Grandmaster pieces, Manticore, Viper armour, Vampire quest sets, many relics) came from Vivek's PC with `tools/pc/extract_on_pc.py` (see below); no item is without an icon now.
- **Two rulesets**: `ng` = first playthrough (`gameplay/items`, `gameplay/abilities`, plus the same in the DLC bundles) and `ng_plus` = New Game Plus (the `*_plus` folders replace the base files of their package). An item identical in both is stored once with `rulesets: ["ng","ng_plus"]`; ids are unique inside a ruleset. In `ng_plus` the same ids are redefined as "legendary" gear (levels 47 to 70) and `NGP X` are carry-over copies of the `ng` item X (`NewGamePlusReplaceItem`, playerWitcher.ws). In `ng` witcher gear has the tiers Basic, Enhanced, Superior, Mastercrafted, Grandmaster (levels 17 to 40) and ONLY the Grandmaster pieces carry `SetBonusPiece`; in `ng_plus` every tier does. The planner lets the player choose the ruleset; the default is `ng` (decision: Vivek).
- **Sets** (`SETS` table in the extractor, by the game's own tags): Feline (`LynxSet`), Griffin, Ursine, Wolven (`WolfSet`, Grandmaster only), Manticore (`RedWolfSet`; the game calls the tag "Red Wolf"), Viper (`ViperSet` armour plus the Viper swords), Forgotten Wolven (`NetflixSet`), Tesham Mutna / Hen Gaidth (`VampireSet`, quest gear with masks), and the plain DLC sets White Tiger, Thousand Flowers, Nine-Tailed Vixen, Scarlet Crest (no set bonus in the scripts). Relics = quality 4 weapons and armour; "Top Notch" generics, `_crafted` duplicates and secondary weapons (axes, maces) are excluded; `quest: true` flags quest items. Masks: only those with a real icon.
- **Set bonuses** (`sets[*].bonuses`; read from `GetSetBonusTooltipDescription`, `playerTypes.ws`, `gameParams.ws` and the ability XML; text from `en.w3strings`, `$S$` filled the way `localizedContent.ws` does). Thresholds: 3 pieces (`ITEMS_REQUIRED_FOR_MINOR_SET_BONUS`, gameParams.ws) and 6 (`..._MAJOR_...`); a piece counts only with the `SetBonusPiece` tag (`UpdateItemSetBonuses`, playerWitcher.ws). `{current}` marks a value the game computes from the pieces worn (value per piece x pieces):

- **Required level** (`required_level`; the game computes it, the XML has none): `inventoryComponent.GetItemLevel` with the steps of `gameParams.GetItemLevel`: armour `floor(1+(armor-25)/5)` (boots and trousers `floor(1+(armor-5)/2)`, gloves `floor(1+(armor-1)/2)`); steel sword `ceil(1+(1+sum(damage_i-1)-25)/8)` over slashing, bludgeoning, rending, elemental, fire, silver, piercing; silver sword the same with 90 and 10 over six types; crossbow by the attack_power multiplier; bolts a fixed level per name minus 14/10/6/4 for quality 5/4/3/2; then minus 1 (at least 1), minus 2 for set gear and 1 for relic, minus 1 more for EP1-tagged gear, minus 3 for `OlgierdSabre`. Steel swords never list SilverDamage and silver swords never SlashingDamage in the stat list. In the list a multiplicative value is a percentage (value x 100, rounded, "NN %"), `focus_gain` is shown as is, everything else is rounded to a whole number (`AddItemStats`, `GetItemTooltipAttributes`). The stat lines come from `gameplay/globals/tooltip_settings.csv` (from the `startup.bundle` of Vivek's PC, imported to `~/incoming/gamedata/csv/`): ONLY the stats listed there are shown, in its row order (94 rows; `stat_display` in `items.json`, and each item stat carries its `line` and `percent`; a stat without `line` is hidden, e.g. `buff_apply_chance`, `staminaRegen_armor_mod`, `ammo`, `item_level_*`), in the colour of its row (`BAADA0` normally, `934913` for the special lines such as experience, gold, dismember and instant-kill chance); percent = the CSV flag, or always for a multiplicative value; `armor_reduction`, `duration`, `toxicity`, `vitality` and the damage types are plain numbers. ## Screens and the Inventory (v28, bar changed in v29)
Three live screens, switched like the game's top bar: `[◀] GLOSSARY · ALCHEMY · INVENTORY · WORLD MAP · QUESTS · CHARACTER · MEDITATION [▶]` (`#topbar`; the active tab is a filled gold block; the arrows step through Glossary, Inventory, Character (`SCR_ORDER`) and skip the four greyed tabs; those say "in game only" and open a centred panel (`igOpen`, reasons in `IG_WHY`) with Open Inventory / Open Glossary; the bar is two rows below 1500 px: tabs, then Level and NG / Copy link; sticky from 600 px; on a phone the tab row scrolls sideways). ## Link segments after the 8 base fields (`g1` v27, `c1` and `s1` v28)
Since v28 the decoder tells the optional segments by their 2-character prefix, not by position: `g1` (gear, below), `c1` + 16 characters (consumables: 8 slots x 2 characters, a number from `data/consumable_ids.json`, 0 = empty, in the order Potion 1-4, Bomb 1-2, steel sword oil, silver sword oil = `CN_SLOTS`; only written when something is set) and `s1` (`s1I` = the Inventory screen is open, `s1G` = the Glossary, v29; absent = Character; the Glossary's sub-tab, selection and search are never in the link). `enc()` writes them in the order g1, c1, s1, so a link without gear, consumables or the Inventory screen is byte-identical to what v27 wrote (`conscheck` re-encodes every fixture link). `dec()` allows up to 16 segments, rejects a known prefix that is malformed or appears twice and any segment that is not `[a-z][0-9][A-Za-z0-9_-]*`, and IGNORES a well-formed segment with a prefix it does not know (a later version's). A consumable number that does not fit its slot (an oil in a potion slot, a silver-only oil on the steel sword) is dropped when the data loads (`cnValidate`). Fixtures: `tests/fixtures/links/v28.*` (consumable links in both rulesets, Inventory links); every older fixture opens on Character with no consumables.

## Gear link format (`g1`, built in v27)
A link is `v1.<skills>.<slots>.<mutagens>.<level>.<bonus>.<researched>.<active>` and, since v27, may end with ONE more segment, `g1<codes>` (so 8 or 9 segments, at most 400 characters); everything before it is untouched. `gearSeg()`, `enc()` and `dec()` in `src/app.js` implement it; `S.gear` holds the 9 numbers and `S.rs` the mode (`ng` or `ng_plus`). Links keep their numbers even when the Equipment screen was never opened (the item lists load on demand); the numbers are validated against the data when Equipment opens.
- **Marker and codes:** `g1`, then ONE character for the ruleset (`A` = ng, `B` = ng_plus: the same item id has different stats in the two rulesets, see Equipment data), then 2 characters per slot, alphabet `A-Za-z0-9-_` (12 bits, 0 = empty, up to 4095 ids), in the fixed slot order steel, silver, crossbow, bolts, chest, gloves, trousers, boots, mask. Example: `...v1.<8 segments>.g1AAAAAAAAAAAAAAAAAAA` adds 22 characters with its dot. The code is a number from an append-only registry `data/item_ids.json` (`data/item_ids.json`, item id string to number, first-seen order, never reused or renumbered, retired items keep their number: rule 10; one number per id, valid in every ruleset that has the id; `tools/extract_items.py` appends new ids and writes each item's `n` into the lists). A tier is a different item, so no tier field. Slot order may only grow at the end.
- **Old links open unchanged (rule 2):** `enc()` writes the `g1` segment only when something is equipped or the mode is New Game Plus, so a link without gear is byte-identical to today's. `dec()` accepts 8 or 9 segments; a 9th that does not start with `g1` is rejected as malformed. The reverse is not possible and not needed: a gear link opened in v26 or older is rejected by their strict `dec()` (more than 8 segments), it does not open a wrong build.
- **Untrusted input (rule 3):** exactly `g1` + a ruleset character + 18 characters from the alphabet (a longer tail is allowed later only by appending slots, and older readers must ignore it); an id that is unknown, retired, not in that ruleset, or belongs to another slot gives an empty slot, never an error or markup.
- **Later changes:** a different layout is `g2` with a migration `g1` to `g2` and fixtures, per "Link compatibility"; `g1` links must keep opening.
- **Tests and fixtures:** `tests/fixtures/links/v27.txt/.json` (25 links: no gear, mode only, every slot alone in both modes, full sets, a mix, the highest numbers, skills + mutagens + gear); every older fixture must still open identically (run_all checks it online and offline); the hostile-link test has bad `g1` segments; `data/item_ids.json` is append-only (checked against `main`, like the fixtures).
- **Not in the link:** runes, glyphs, dyes. The required level is in the data, not the link.
- (v27's skills scale `fitSkills` and the panel scroll no longer exist: the Character screen is the v26 layout again and the Inventory screen scrolls with the page.)
- **Which worn pieces count for a set** (the game): every equipped item carrying the `SetBonusPiece` tag, whatever its slot (`UpdateItemSetBonuses`, playerWitcher.ws:10972-10987, tag name gameParams.ws:345). In the data the set crossbows never carry it (so they never count) and the Vampire masks do; first-playthrough witcher gear carries it only at Grandmaster. The set card names each uncounted piece and the real reason (`eqWhy`).
- **Level requirement** (the game: `HasRequiredLevelToEquipItem`, r4Player.ws:11723, blocks an item when `GetItemLevel(item) > GetLevel()`; the same test colours the level red, inventoryComponent.ws:409): the planner compares only its **Level** field (`lvl()`), never bonus points. A too-high item shows its level in red, Equip is disabled with "Requires level N", Equip set equips only the pieces the level allows and lists the skipped ones, and autogen relics ("Level varies") are never blocked (the level is rolled when the item drops). Gear already worn is never removed when Level goes down (links stay stable): the slot gets a red border, a "Level too low" badge and a warning line. Masks need level 1 (no branch in `GetItemLevel`), bolts are tested like every other slot. Not modelled: the Wolf Hour potion (-2 levels) and the NG+ start level (the game adds start level - 30 required levels to non-autogen gear it picks up; `required_level` is the value at start level 30).
